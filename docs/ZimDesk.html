🗺️ Mapa Funcional — Módulos de la Aplicación

Roles del sistema

Admin

Gestión total. Mantiene usuarios, categorías, departamentos, FAQs, normas. Asigna agentes a tickets. Visualiza métricas y SLA.

Agent

Ve sus tickets asignados. Responde tickets. Cierra tickets. Visualiza dashboard propio con métricas por mes.

Client

Crea tickets con archivos adjuntos. Consulta estado de sus tickets. Responde mensajes. Descarga PDF. Reabrir tickets cerrados.

⚖️ ¿Migrar a React + Next.js + PostgreSQL + Docker?

Stack propuesto

React 18+ Next.js 14+ (App Router) TypeScript PostgreSQL Docker + Docker Compose Prisma ORM / Drizzle NextAuth.js / Auth.js Tailwind CSS

Frontend: Laravel Blade → React + Next.js

Pros
  • Componentes reutilizables — el dashboard triplicado por rol se unifica con props
  • UX reactiva sin recargas de página (SPA parcial)
  • Ecosistema masivo: shadcn/ui, Radix, Recharts para gráficos
  • TypeScript elimina errores de tipo en runtime
  • Server Components (Next.js) = SSR sin bundle extra en cliente
  • Better DX: hot reload, Turbopack, error overlays
Contras
  • Curva de aprendizaje si el equipo solo conoce Blade
  • El App Router de Next.js tiene complejidad nueva (server vs client components)
  • Más boilerplate inicial que Blade para formularios simples
  • SEO no es prioritario para un sistema interno — SSR es un beneficio menor

Backend: PHP/Laravel → API Routes Next.js / Laravel API

Opción A — Mantener Laravel como API REST
  • Reutiliza toda la lógica de negocio existente (emails, logs, PDF)
  • Menor riesgo: solo migras el frontend
  • Sanctum ya soporta SPA auth
  • Laravel Queues para emails asíncronos
Opción B — Migrar a Next.js full-stack (API Routes + Server Actions)
  • Elimina PHP completamente — un solo lenguaje (TypeScript)
  • Server Actions simplifican mutaciones sin API explícita
  • Pero: reescritura total del backend (meses de trabajo)
  • DomPDF → alternativas JS (Puppeteer, @react-pdf) menos maduras

Base de Datos: MySQL → PostgreSQL

Pros de PostgreSQL
  • Columnas JSONB nativas — útil para campos dinámicos futuros
  • Full-text search integrado — reemplaza LIKE en búsquedas
  • Tipos avanzados: arrays, enum nativo, UUID
  • Mejor concurrencia bajo alta carga
  • Prisma ORM tiene soporte excelente con PG
  • Estándar en Vercel, Railway, Supabase — deploy más fácil
Contras
  • Migración de datos requiere testing exhaustivo
  • Algunas queries MySQL con ISNULL() difieren en PG (IS NULL)
  • Si el hosting actual solo ofrece MySQL, hay costo extra

Contenedores: Sin Docker → Docker + Compose

Pros de Docker
  • "Funciona en mi máquina" se elimina — paridad total dev/prod
  • Onboarding nuevos devs en minutos: docker compose up
  • Servicios aislados: app, db, redis, mailhog
  • CI/CD con GitHub Actions + Docker Hub
  • Escalabilidad horizontal con Kubernetes futuro
Contras
  • Overhead de configuración inicial (~1 semana)
  • Mayor uso de RAM en desarrollo local
  • Hosting compartido (cPanel) no soporta Docker

🎯 Veredicto & Recomendación Estratégica

Recomendado

Migración Progresiva — Opción A

Backend: Mantener Laravel 10/11 como API REST. Agregar Queues (Redis), caché y tests.

Frontend: Migrar de Blade a React + Next.js App Router (TypeScript + Tailwind).

DB: Migrar a PostgreSQL al mismo tiempo que se Dockeriza.

Infra: Docker Compose para dev. Deploy en Railway / Render / VPS con contenedores.

No Recomendado

Big Bang Rewrite — Opción B

Reescribir todo en Next.js full-stack elimina toda la lógica de negocio estable (emails, PDF, logs, SLA) y multiplica el riesgo.

Solo válido si el equipo tiene experiencia fuerte en TypeScript backend y el sistema está en versión 0.

📐 Buenas Prácticas — Lo que hay que resolver sí o sí

01 · Backend
Eliminar IDs hardcodeados de estados
Reemplazar status_id = 2 por Status::where('slug', 'en_progreso')->first()->id o agregar constantes en el modelo. Un seed diferente rompe toda la lógica.
02 · Performance
Activar colas asíncronas
Cambiar QUEUE_CONNECTION=redis y enviar todos los emails con Mail::queue(). El usuario no debe esperar el envío SMTP para ver la respuesta del servidor.
03 · Arquitectura
Extraer lógica de negocio a Services
El TicketController tiene ~400 líneas con lógica mezclada. Crear TicketService, NotificationService y LogService para separar responsabilidades y permitir testing.
04 · Seguridad
Autorización con Policies, no solo middleware
El middleware de rol protege rutas pero dentro de los métodos no hay validación de que el usuario pueda acceder a ese ticket específico. Un client podría acceder al PDF de otro si adivina el ID.
05 · Base de Datos
Agregar índices en columnas de filtrado
Las columnas status_id, priority_id, assigned_to, user_id en la tabla tickets son usadas en WHERE constantemente. Sin índices, cada filtro hace full scan.
06 · Testing
Cubrir el flujo de tickets con Feature Tests
Con Pest o PHPUnit, testear el ciclo completo: crear → asignar → responder → cerrar. Garantiza que ningún refactor rompe el core.
07 · Frontend
Componentes en React con estado local
El dashboard triplicado (admin/agent/client) con lógica duplicada se unifica con un componente <TicketStatsGrid role={role} data={data} />. Elimina ~300 líneas de Blade repetidas.
08 · Observabilidad
Separar log de sistema del log de tickets
Ya existe la tabla system_logs pero no se usa consistentemente. Centralizar errores en un canal dedicado (Sentry o Laravel Telescope) para ver errores en producción.
09 · DevOps
Variables de entorno y secretos seguros
El archivo .env.template contiene contraseñas reales (SMTP, DB). Nunca commitear credenciales. Usar .env.example con valores vacíos y gestionar secretos con GitHub Secrets o Vault.
10 · SLA
Alertas y umbrales de SLA configurables
El campo first_response_at existe pero no hay alertas si un ticket lleva X horas sin respuesta. Agregar job programado que notifique al admin cuando se supera el umbral.

🚀 Plan de Migración por Fases

1
Fase 1 Saneamiento del código actual 2–3 semanas
Antes de migrar, limpiar las deudas técnicas para que la base sea sólida.
  • Reemplazar IDs hardcodeados de estados por constantes o slugs
  • Crear TicketService y NotificationService extrayendo lógica del controlador
  • Agregar Laravel Policies para autorización a nivel de recurso
  • Activar Redis + queues para envío asíncrono de emails
  • Agregar índices de base de datos en columnas de filtrado frecuente
  • Limpiar .env.template eliminando credenciales reales
2
Fase 2 Dockerización del entorno 1 semana
Crear infraestructura reproducible para desarrollo y base para producción.
  • Crear docker-compose.yml con servicios: app (PHP-FPM), nginx, mysql, redis, mailhog
  • Migrar base de datos a PostgreSQL (ajustar queries incompatibles)
  • Configurar Dockerfile optimizado para producción (multi-stage build)
  • Documentar comandos de arranque en README
3
Fase 3 Convertir Laravel en API REST 2–3 semanas
Preparar el backend para ser consumido por el nuevo frontend React.
  • Crear API Resources (TicketResource, UserResource, etc.) para serialización consistente
  • Mover todas las rutas a routes/api.php con prefijo /api/v1/
  • Configurar Laravel Sanctum para SPA (cookie-based auth)
  • Agregar paginación API, filtros como query params, responses estandarizadas
  • Escribir Feature Tests de los endpoints principales con Pest
  • Documentar la API con Laravel Scribe o Swagger
4
Fase 4 Nuevo Frontend: Next.js + React 6–8 semanas
Construir el frontend desde cero en Next.js 14 con App Router.
  • Setup: Next.js 14, TypeScript, Tailwind CSS, shadcn/ui, TanStack Query
  • Autenticación: NextAuth.js con provider Credentials → Laravel API
  • Layout base con sidebar responsive (igual al Velzon actual)
  • Módulo Tickets: listado, creación (drag & drop archivos), detalle con hilo de mensajes
  • Dashboard unificado por rol con Recharts para gráficos
  • CRUD de mantenimiento (Usuarios, Categorías, Departamentos, FAQs)
  • Editor de normas de plataforma
  • Perfil de usuario con upload de avatar
5
Fase 5 Real-time & Features avanzadas 2–3 semanas
Agregar las capacidades que la versión actual no tiene.
  • Notificaciones en tiempo real con Laravel Echo + Pusher / Soketi (self-hosted)
  • Alertas SLA: job programado que detecta tickets sin respuesta > N horas
  • Búsqueda full-text en tickets con PostgreSQL FTS
  • Exportación CSV/Excel de listados
  • Modo dark/light toggle persistente
6
Fase 6 CI/CD & Deploy 1 semana
Automatizar el pipeline de despliegue.
  • GitHub Actions: lint → test → build → deploy en cada PR a main
  • Frontend: Vercel o Cloudflare Pages
  • Backend API: Railway / Render / VPS con Docker
  • Base de datos: Supabase (PostgreSQL managed) o Neon.tech
  • Secretos: GitHub Secrets + .env en plataforma de hosting
  • Staging environment separado de producción

💡 Conclusión

ZimDesk es una aplicación funcional y bien estructurada para ser un sistema de mesa de ayuda interno. El modelo de datos es sólido, el sistema de logs y emails es completo, y la separación por roles está bien implementada.


La migración a React + Next.js + PostgreSQL + Docker es estratégicamente correcta para escalar el sistema. El punto más crítico no es el stack sino el orden: limpiar primero, luego dockerizar, luego exponer la API, y finalmente construir el nuevo frontend. Intentar hacer todo en paralelo es el error más común y más costoso.


La deuda técnica más urgente a resolver antes de cualquier migración es: colas asíncronas para emails, authorization policies e IDs de estado hardcodeados. Todo lo demás es mejora incremental.
