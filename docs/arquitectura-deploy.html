🏗️ Patrón Fullstack Monolítico

ZimDesk utiliza Next.js como framework único que maneja tanto la interfaz como la lógica de servidor. No hay un backend separado — todo convive en el mismo repositorio y proceso.

Beneficios del patrón

Beneficio Detalle
⚡ Un solo deploy Frontend + backend en la misma imagen Docker. Un solo npm run build, una sola unidad de despliegue.
🔄 Sin latencia interna Las API Routes corren en el mismo proceso. No hay round-trip HTTP entre frontend y backend como ocurriría con Express separado.
🔷 TypeScript compartido Los tipos definidos en src/types/index.ts se usan tanto en UI como en los endpoints. Sin duplicar interfaces.
🗄️ SSR directo a la DB Los Server Components pueden consultar Prisma directamente, sin pasar por la API REST. Reduce una capa completa de I/O.
📦 Menos infraestructura No hay que gestionar dos servidores, dos pipelines de CI/CD ni dos dominios. El docker-compose.yml levanta todo.

Limitaciones (y por qué no importan en ZimDesk)

Limitación

Escalado acoplado

No se puede escalar el backend de forma independiente al frontend — se escala todo junto.

Por qué no importa aquí

ZimDesk es un sistema interno

El volumen de usuarios es bajo y predecible. Escalar la app entera es suficiente y mucho más simple.

Limitación

Caída total si falla el proceso

Si el servidor Next.js cae, tanto la UI como la API dejan de responder.

Por qué no importa aquí

Docker con restart automático

El docker-compose.yml tiene restart: unless-stopped. El contenedor se recupera solo ante fallos.

🖥️ ¿Se puede deployar en Hostinger?

Depende del tipo de hosting. Next.js necesita un proceso Node.js corriendo de forma persistente — no es un archivo PHP que se ejecuta por request.

❌ Shared Hosting

No funciona

El shared hosting de Hostinger usa Apache + PHP. No soporta procesos Node.js persistentes. Intentar correr Next.js acá va a fallar.

Apache/PHP Sin Node.js No compatible
✅ VPS (KVM)

Funciona perfectamente

El VPS da acceso root completo a Linux. Se puede instalar Docker, Node.js y PostgreSQL. El proyecto ya tiene Dockerfile listo.

Root access Docker PostgreSQL

Pasos para deployar en Hostinger VPS

1
Instalar Docker en el VPS curl -fsSL https://get.docker.com | sh — instala Docker Engine y Docker Compose en un solo comando.
2
Clonar el repositorio git clone https://github.com/MatiasNZamora/ZimDesk_V2.git en el servidor.
3
Crear el archivo .env de producción Copiar .env.example a .env y completar con las credenciales reales: DATABASE_URL, NEXTAUTH_SECRET, MAIL_*.
4
Aplicar migraciones de base de datos docker compose run --rm app npx prisma migrate deploy
5
Levantar la app docker compose up -d — levanta la app, PostgreSQL y Redis en segundo plano.
6
Configurar Nginx como reverse proxy Apuntar el dominio o IP al puerto 3000 con Nginx. Opcionalmente agregar SSL con Let's Encrypt (certbot).

Recomendación

Vercel para empezar, VPS cuando escale

El proyecto ya tiene vercel.json con los cron jobs configurados. Vercel es la opción de menor fricción para el primer deploy. Si en el futuro se necesita más control o la DB cuesta mucho externa, migrar a un VPS con Docker es sencillo.

🐛 Bug Detectado — Fix Requerido

🚨
El Dockerfile falla sin esta configuración

El Dockerfile copia .next/standalone en la imagen de producción, pero next.config.js no tiene output: 'standalone'. Next.js no genera esa carpeta y el build de Docker falla.

Dónde está el problema

# Dockerfile línea 20 — copia algo que no existe sin el fix:
COPY --from=builder --chown=nextjs:nodejs /app/.next/standalone ./

Fix: agregar output: 'standalone' en next.config.js

// next.config.js
const nextConfig = {
output: 'standalone', // ← esta línea faltaba
  images: {
    remotePatterns: [
      { protocol: 'http', hostname: 'localhost' },
    ],
  },
  experimental: {
    serverActions: { allowedOrigins: ['localhost:3000'] },
  },
}

module.exports = nextConfig
⚠️
Sin este fix, docker compose up en producción fallará

El build en modo dev (npm run dev) funciona igual. El problema solo aparece al construir la imagen Docker de producción.
